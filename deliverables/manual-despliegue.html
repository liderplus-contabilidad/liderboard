01 Requisitos

Lo que hace falta en el equipo de quien desarrolla. Para desplegar no se necesita nada instalado: eso lo hace Vercel.

Requisito Versión Nota
Node.js ≥ 20.9.0 Lo exige Next 16. Se recomienda la LTS vigente, que es lo que usa la integración continua (lts/*).
pnpm 11.15.0 Fijado en package.json (packageManager). Con Corepack activo (corepack enable) se instala solo la versión correcta. No usar npm ni yarn: romperían el lockfile.
Git — El despliegue se dispara desde el repositorio.
Navegador Moderno de escritorio La app usa IndexedDB y es solo de escritorio: no hay capa móvil.
Recomendación

El proyecto no declara un campo engines, así que nada impide instalarlo con una versión de Node más vieja de la que Next admite y descubrirlo recién al construir. Agregar "engines": { "node": ">=20.9.0" } a package.json hace que el error salga en el install, y Vercel lo respeta al elegir su runtime.

02 Instalación local

Tres comandos. No hay archivo .env que copiar ni base de datos que levantar. 

# 1 · Clonar el repositorio
git clone <url-del-repositorio> liderboard
cd liderboard

# 2 · Activar la versión de pnpm que el proyecto fija
corepack enable

# 3 · Instalar dependencias exactamente como están en el lockfile
pnpm install --frozen-lockfile

# 4 · Levantar el servidor de desarrollo (Turbopack) en :3000
pnpm dev

La aplicación abre en http://localhost:3000 y redirige a /profit-loss, el módulo por defecto. Arranca vacía: no hay datos de ejemplo porque no hay base de datos compartida — el primer cliente o el primer hotel los crea el usuario, y lo que cargue queda en su propio navegador.

Sobre la instalación

Dos dependencias necesitan ejecutar scripts al instalarse (sharp y unrs-resolver). Ya están autorizadas en pnpm-workspace.yaml, que está versionado, así que la instalación no se detiene a pedir aprobación ni en el equipo local ni en Vercel.

03 Comandos

Los scripts de package.json, en orden de uso.

Comando Qué hace
pnpm dev Servidor de desarrollo con Turbopack en el puerto 3000.
pnpm build Build de producción. También verifica los tipos: un error de TypeScript rompe el build.
pnpm start Sirve el build de producción. Requiere haber corrido pnpm build antes.
pnpm lint oxlint. No es ESLint: ejecutar eslint falla porque no está instalado.
pnpm fmt oxfmt. pnpm fmt:check es la compuerta que corre en CI.
pnpm test Vitest sobre la capa pura (lib/**/*.test.ts).

04 Cuenta y accesos

El proyecto debe vivir bajo la cuenta de Vercel de la empresa, no bajo una cuenta personal.

Esto no es una formalidad: quien es dueño del proyecto en Vercel controla el dominio, los despliegues y la facturación. Un proyecto alojado en la cuenta personal de un desarrollador deja a la firma sin acceso el día que esa persona ya no esté, y transferirlo después exige que esa misma persona lo autorice.

  • Titular: el equipo (Team) de la empresa en Vercel. Los desarrolladores entran como miembros de ese equipo, no como dueños.
  • Repositorio: la integración de Git debe autorizarse contra el repositorio de la organización, no contra un fork personal.
  • Dominio: se configura en Project → Settings → Domains. El DNS lo administra quien tenga el dominio de la firma.
  • Si el proyecto ya existe en una cuenta personal: se traslada con Settings → Advanced → Transfer Project; conserva el historial de despliegues y los dominios se vuelven a verificar.

05 Despliegue en Vercel

Configuración inicial. Una vez hecha, cada push despliega solo.

  1. Importar el repositorio

    En el equipo de la empresa: Add New → Project y elegir el repositorio. Vercel detecta Next.js y pnpm por el lockfile; el preset correcto es Next.js.

  2. Confirmar los ajustes de build

    Los valores por defecto ya son los correctos. Solo conviene verificarlos:

    Ajuste Valor
    Framework Preset Next.js
    Build Command pnpm build
    Install Command pnpm install --frozen-lockfile
    Output Directory (por defecto)
    Root Directory ./

  3. Fijar la versión de Node

    En Settings → Node.js Version, elegir una versión 20.9 o superior. Dejarla fijada evita que una actualización de la plataforma cambie el runtime debajo del proyecto sin aviso.

  4. Variables de entorno: ninguna

    No hay nada que cargar en Settings → Environment Variables. La sección 07 explica por qué, y merece leerse antes de agregar la primera.

  5. Definir la rama de producción

    main es la rama de producción; cada pull request genera además un despliegue de vista previa con su propia URL, útil para que la firma revise un cambio antes de que llegue al dominio real.

  6. Desplegar y asignar el dominio

    El primer deploy arranca al importar. Con él verde, se asigna el dominio en Settings → Domains.

Relación con la integración continua

GitHub Actions y Vercel construyen por separado: Actions corre lint, formato, build y pruebas en cada PR y en cada push a main; Vercel corre su propio build para publicar. Vercel no ejecuta las pruebas, así que un despliegue puede salir verde con la suite en rojo. La compuerta de calidad es Actions, y por eso conviene exigir que sus cuatro trabajos pasen antes de fusionar a main.

06 Por qué hace falta Node

La aplicación no tiene backend, pero tampoco puede publicarse como sitio estático. Conviene entender por qué antes de intentar abaratarlo.

La intuición razonable es que una app cuyos datos viven en el navegador debería poder servirse desde cualquier hosting de archivos. No es el caso hoy, y la razón es concreta: Rol de Pagos tiene dos niveles de ruta dinámica — 

app/(dashboard)/payroll/[periodId]/page.tsx
app/(dashboard)/payroll/[periodId]/[employeeId]/page.tsx

— y un export estático (output: "export") exige que cada ruta dinámica enumere sus valores posibles en tiempo de build, con generateStaticParams. Aquí es imposible: esos identificadores son UUID que se generan en el navegador del usuario y viven en su IndexedDB. En build no existen todavía y nunca serán los mismos para dos usuarios.

Por eso el despliegue necesita el runtime de Next, que es exactamente lo que Vercel provee sin configuración. Migrar a estático sería posible, pero exigiría rediseñar esas rutas para que el identificador viaje fuera del path; no es un cambio de configuración.

07 Los datos no se despliegan

La consecuencia operativa más importante de la arquitectura, y la que hay que explicarle a quien use el sistema.

Toda la información contable vive en IndexedDB, dentro del navegador de cada usuario. No hay base de datos en el servidor. De ahí salen cinco hechos que gobiernan la operación:

  • Un despliegue no toca los datos. Publicar una versión nueva no migra, no borra y no respalda nada: lo que cada usuario cargó sigue igual.
  • Los datos no se comparten entre personas. Dos contadores del mismo equipo no ven lo mismo, aunque abran la misma URL. Lo que se comparte es el archivo Excel.
  • Ni entre navegadores o equipos. Cambiar de Chrome a Firefox, de máquina o de perfil equivale a empezar vacío.
  • Borrar los datos del sitio borra el trabajo. «Limpiar datos de navegación» con el sitio incluido elimina la base. No hay copia en ningún otro lado.
  • El respaldo es la descarga a Excel. Está diseñada para eso: todo archivo que la app descarga vuelve a entrar sin pérdida, comentarios y ajustes incluidos. Conviene establecer con la firma la costumbre de descargar al cerrar cada mes.
Migraciones de esquema

Cuando una versión nueva cambia la estructura de la base, la migración se ejecuta en el navegador de cada usuario, la primera vez que abre la app después del despliegue. No hay un momento de mantenimiento ni una migración central que correr.

Y no tiene vuelta atrás: IndexedDB no permite bajar de versión. Volver la aplicación a un despliegue anterior no revierte una migración ya aplicada en el navegador de alguien. Por eso toda migración del proyecto está escrita para ser aditiva —nunca borra en el mismo paso en que crea—, y por eso un cambio de esquema merece verificarse en una vista previa antes de llegar a main.

08 Verificación y rollback

Qué comprobar con el despliegue en verde, y qué hacer si algo salió mal.

Lista de verificación

  • El dominio carga y redirige a /profit-loss.
  • Los tres módulos abren desde el menú lateral: Pérdidas y Ganancias, Ocupaciones y Rol de Pagos.
  • Con datos ya cargados en ese navegador, siguen ahí después del despliegue.
  • Una carga de Excel funciona de extremo a extremo en cualquiera de los tres módulos.
  • Una descarga a Excel se genera y vuelve a subirse sin errores.
  • El comprobante en PDF de Rol de Pagos se descarga y abre.
  • Los gráficos se dibujan y las tipografías de sus ejes se ven correctas, no con una fuente de reemplazo.

Rollback

En Deployments, cualquier despliegue anterior se promueve a producción con Promote to Production. Es inmediato y no requiere reconstruir.

Límite del rollback

Revertir la aplicación no revierte una migración de datos que ya corrió en el navegador de un usuario. Si la versión defectuosa cambió el esquema, volver atrás deja a esa persona con una base más nueva que el código que la lee. Ante un fallo en un despliegue que tocó el esquema, la salida es corregir hacia adelante, no hacia atrás.
